# Console app (`src/`) — AGENTS.md

Ink/React TUI for the TurboPanel dev environment. Repo context:
`../AGENTS.md`.

**Entry points:** normal mode enters through `src/tui.tsx`; watch mode enters
through `scripts/hot-reload.tsx`, which hot-loads `src/app.tsx` through the
Vite module graph and rerenders the existing Ink instance. Keep interactive
shell state in `scripts/hot-reload.tsx` or another stable runtime layer if it
must survive UI edits. Run via `vite-node` (Node). Components live in
`src/components/`, hooks in `src/hooks/`, helpers in `src/lib/` — read the
directory rather than a checked-in tree, which goes stale.

Keep interactive shell state in `scripts/hot-reload.tsx` or another stable runtime layer if it must survive UI edits.
- The `@turbopanel/components/` import alias is defined in **both** `vite.config.ts` (`resolve.alias`) and `tsconfig.json` (`paths`) — keep them in sync.
- Keep the CLI **simple**. Platform repo install, service monitoring, and stack actions belong in the Ink app — not new shell scripts.
- **`src/lib/paths.ts`** — `TURBOPANEL_TRUNK_BRANCH` (`trunk`) is the dev shim for git checkouts and `TURBOPANEL_TRUNK_BRANCH` in `/etc/turbopanel/daemon.env`; release/binary installs omit it. Path helpers: `resolveDevRoot()`, `platformRepoPath()`, `TURBOPANEL_DEV_ROOT`, `TURBOPANEL_<DIR>_REPO` env overrides. Mutable data: `CONFIG_DIR=/etc/turbopanel`, `STATE_DIR=/var/lib/turbopanel`, `LOG_DIR=/var/log/turbopanel`, `RUNTIMES_DIR=/opt/turbopanel/vendor`. Workers-mode `platformCaCertPath()` is the durable bundle (`/var/lib/turbopanel/tls/ca-bundle.pem`), not checkout `certs/ca.crt`. Daemon: `DAEMON_ENV_PATH=/etc/turbopanel/daemon.env`, `DAEMON_LOG_PATH`/`DAEMON_ERR_LOG_PATH`=`/var/log/turbopanel/daemon.log` + `daemon.err.log`. Console logs: `consoleLogDir()` → `~/.local/console`. `DENO_VERSION` (**`2.9.8`**) is the console's bootstrap fallback + status label and **must** match `deno_version` in the daemon's `deno-runtime` role (pinned by the daemon's `src/orchestration/paths.test.ts`). The daemon systemd unit name is **`turbopaneld`** (`DAEMON_SYSTEMD_UNIT`), matching the daemon's `install-daemon-systemd.sh` and managed production installs.
- **`src/lib/developer-client.ts`** — `readInstanceSecret()` resolves the Local-Console HMAC key from the **current (first) entry of `/etc/turbopanel/instance/.instance_secrets`** when that file exists and is readable — a present-but-unreadable keyring must not silently sign with a stale or guessed key. **Why:** `turbopanel/src/developer/local-console-auth.ts` verifies against `versioned[0]` only, so without this the console would 401 after any rotation.
- **`src/lib/daemon-exec.ts`** — always resolves a **Deno** invocation of the source-checkout scripts (`scripts/bootstrap-orchestration.ts`, `scripts/run-orchestration-action.ts`). Resolution (`resolveBootstrapDenoBin`) is **pin-first**: a host Deno on PATH stays the default but only while it reports `DENO_VERSION`; otherwise the vendored pin wins — `/opt/turbopanel/vendor/deno/current/deno` only once `current` is known to report the pin, else the versioned `/opt/turbopanel/vendor/deno/<DENO_VERSION>/deno` directly, so a `current` left behind by a superseded pin is never exec'd. A mismatched host Deno is the last resort before throwing. `ensureOrchestrationDenoBin` now runs before every orchestration invocation (`runOrchestrationAction` in `src/lib/instance-install.ts`), so Deno self-heals on Converge/playbook actions, not just daemon bootstrap. It never runs `/opt/turbopanel/bin/turbopaneld` or `turbopaneld.js`; those managed/production ExecStart modes are outside this console. Deno install/upgrade logic still must **not** live in `./console` or `scripts/lib/runtime.sh` — those stay Node-only; the ensure step is orchestration-path only. `ensureBootstrapDeno` vendors from **`dl.deno.land`** (same CDN as daemon `run.sh` / `deno-runtime`), not `github.com/.../releases/download` (flaky 503s from VMs). It short-circuits on a host Deno only when that host *is* the pin — a mismatched host warns (`Host Deno <version> does not match pinned <DENO_VERSION> — vendoring pinned Deno for orchestration parity`) and falls through to vendoring the pinned version — and when the pinned binary is already present it still repairs drifted `current` / `bin/deno` symlinks (mirrors `tp_install_deno_runtime` in the daemon's `scripts/run.sh`).
- **Dev environment readiness** — `src/lib/dev-env-readiness.ts` exports `resolveDevEnvStartupPlan`: **bootstrap** when checkout/Deno/ansible/unit are missing; otherwise **idle** (no auto-converge on launch). Wired from `initialAutoInstallState()` / `useConsoleApp`. Converge is explicit via Developer → Converge (optional-services picker first) or the post-bootstrap chain. Preferences live in `~/.local/console/optional-services.json` (`src/lib/optional-dev-services.ts`). Drizzle Studio and Mailpit (`smtp`) remain on the Services list in gray when deselected; **E** / **X** persist into that prefs file so the next converge does not revert them. Picker defaults: UI, website, Mailpit, and Drizzle Studio on; Redis Insight off.
- **Bootstrap failures** — `bootstrapOrchestration()` (`src/lib/daemon-install.ts`) feeds every non-event output line into `BootstrapOutputCollector` (`src/lib/bootstrap-failure.ts`). On a non-zero exit it writes the whole output to `CONSOLE_BOOTSTRAP_LOG` (`<dev root>/.local/console/bootstrap-orchestration.log`, or, when that cannot be written, a new private `turbopanel-bootstrap-*` folder in the temp folder, file mode 0600; the daemon's failure line carries the whole command line, so bootstrap commands must never carry secrets) and rejects with `Bootstrap failed (exit N): <the daemon's ✗ or [bootstrap] line>` plus `Full output: <path>`. The daemon prints its failure line and then the failing command's last lines on stderr, so the last stderr line (for example uv's `+ yamllint==…`) is never the error. The provisioner's failure view keeps the last 20 output lines (`OUTPUT_LOG_ROWS`).
- **`instance-dev-install --if-needed`** — `installDevEnvironment(..., mode)` defaults to `"force"` for legacy callers (reset/provisioner) and for Developer → **Converge / re-converge** (`start-dev-env`). Uses `"if-needed"` for the daemon-install-finished chain (`handleDaemonInstallDone` → optional-services picker → `startDevEnvConverge("if-needed")`). Force mode sets `TURBOPANEL_FORCE_CONVERGE=1` via `orchestrationEnv()` so the daemon playbook always runs; `if-needed` lets the daemon skip when the converge stamp matches (see `../turbopaneld/orchestration/AGENTS.md`). The optional-tooling selection is sent as one structured payload (`TURBOPANEL_DEV_CONVERGE_OPTIONS`, JSON `{ optionalServices: { <ansibleStem>: bool } }` from `devConvergeOptionsEnvEntry()` in `src/lib/optional-dev-services.ts` — the only optional-service catalog); the daemon's `run-orchestration-action.ts` parses it once into a single Ansible extra-vars object so deselected units (dbstudio / mailpit / ui / website / redis-insight) stay stopped. Default **Deno** converge sets `TURBOPANEL_SYSTEM_EMAIL__PROVIDER=mailpit-smtp` and `MAILPIT_SMTP_PORT` on `turbopanel-instance` (via `instance-launch`); **Workers** dev uses `mailpit-api` + `MAILPIT_API_URL` in `.dev.vars` — see `src/lib/dev-converge-email-settings.test.ts`.
- **Cell trace (Developer area)** — the Developer menu (`src/lib/daemon-actions.ts` → `toggle-cell-trace` / `view-cell-trace` actions, dispatched in `src/hooks/use-console-app.ts`) lets you enable/disable verbose cell tracing and view it. The toggle (`src/lib/instance-trace-env.ts` — `readCellTraceEnabled`/`setCellTraceEnabled`) writes `TURBOPANEL_DAEMON_DEBUG` into **both** `/etc/turbopanel/instance/runtime.env` and `runtime.dev-vars` (so it applies to Deno and the Workers `wrangler dev` DO identically) and then restarts `turbopanel-instance` (reusing the existing restart-overlay flow) to apply it. The **Cell trace** viewer (`src/components/cell-trace-view.tsx`, `src/hooks/use-cell-trace-log.ts`, `src/lib/cell-trace-log.ts`) is a Developer sub-view that tails and filters the instance log (`/var/log/turbopanel/instance/instance.log` + `.err.log`) down to the `daemon-cell`/`command-consumer`-tagged trace lines, reached via the `view-cell-trace` action and rendered by `src/components/developer-panel.tsx`. Enabling `TURBOPANEL_DAEMON_DEBUG` now also surfaces per-call-site Durable Object storage-op counters (`storageReads`/`storageWrites`/`storageByCallSite`) on the cell diagnostics for billing audits; canonical detail lives in `~/turbopanel/turbopanel/AGENTS.md` (Daemon Cell).
- **Run tests (Developer area + Services T)** — Developer → **Run tests…** (`run-tests`) opens a sub-view (`src/components/run-tests-view.tsx`) to pick a present checkout (`turbopaneld` / `turbopanel` / `ui` / `website` / `dev`) and a suite, then streams output via `runCaptured` inside the guest/VM (vendored `pnpm` or host/vendored `deno task`). On the **Services** screen, **L** opens the external log pager (`less` / `tail`); **T** on instance, daemon, caddy (control-plane Caddy → instance checkout), ui, or website skips the repo picker and offers that checkout's suites. Catalog + runner: `src/lib/run-repo-tests.ts`. Every run also writes a full transcript to `~/.local/console/test-runs/<repo>-<suite>-<timestamp>.log` and overwrites `~/.local/console/last-test-run.log` (`src/lib/test-run-log.ts`); the TUI prints those paths when finished. Esc cancels an in-flight run (AbortSignal → SIGTERM) or steps back; Enter re-runs after completion. Every checkout offers **CI verify** (`verify:ci` — the GitHub Actions verify/build job minus the Sonar upload) and **Coverage** (`test:coverage`, the same LCOV CI imports). Instance also offers `test:do` / `test:hook`. Non-interactive: `scripts/ci-verify.sh` (from the host it `vagrant ssh`s into the guest).
- **Rebuild daemon and upgrade connected servers** — Developer → **Rebuild daemon and upgrade connected servers** (`rebuild-daemon-upgrade`) runs `deno task release:dev` in `~/turbopanel/turbopaneld` (compile + overlay `dist/channels.json` / `manifest.json` with relative artifact URLs) then `POST /api/developer/v1/daemon/update`. Connected **remote** servers download those artifacts from this instance (`TURBOPANEL_DL_BASE`); the co-located daemon is skipped (it runs from source). Overlay identity is `<git-sha>+<unix-seconds>` so each rebuild is newer than remotes that already baked the previous overlay of the same HEAD. The provisioner stays on screen until a keypress so compile/update output is readable. This must **not** run daemon bootstrap, the optional-services picker, or a local converge — set `daemonOperation` before switching to the bootstrap area so Ink does not mount ProvisionerPanel in the default `"daemon"` phase. **Sync source to attached checkouts** (`sync-dev-build`) remains the source-tarball path for daemons that still have a checkout.
- **Web interface Build and Push Daemon** — a development control plane never checks for updates and never updates on its own. Admin › Updates shows every piece as running from the checkout and a **Your Servers** card with **Build and Push Daemon**: `POST /api/admin/v1/instance/updates/development/push` (superadmin only, registered only from `deno-dev.ts`) runs `deno task release:dev` in the daemon checkout when its source changed since the last build (source fingerprint from `~/turbopanel/turbopaneld/scripts/source-fingerprint.ts`; keep it identical to the control plane's `computeDaemonSourceFingerprint`), then sends update envelopes to every connected remote server in parallel; `GET …/development` reports the build, each remote server's daemon commit and the job. The update banner and the logo indicator light only while a connected remote server lacks the checkout's daemon changes. The console **U** action is the terminal path to the same build and fan-out through the developer API; do not run it while a web push is building, as both write `turbopaneld/dist/`. The same card offers **Update and Restart** and **Restart Only** for this development host itself (see the next note); the control plane refuses a host job while its Build and Push job runs, and the other way round.
- **Development host status and update (Services rows + Developer area)** — the co-located daemon (`../turbopaneld/src/dev-host/`) watches the four checkouts behind the daemon, control plane (`instance` row), web interface (`ui` row) and website rows and writes the whole status atomically to `/var/lib/turbopanel/dev-updates/status.json` (plus `writtenAt`) on every change and at least once a minute. The console only **reads** that file (`src/lib/dev-host-status.ts`, parsed leniently: a missing file, bad JSON or an unknown value shows nothing rather than failing) through one shared store (`src/lib/dev-host-store.ts`, hook `src/hooks/use-dev-host-status.ts`): one file read every 15 s while a panel shows it, every 2 s while a fresh file shows a job running or just after one was started, no subprocess. The store notifies when the content, its staleness or the job line's visibility changes, so notes and lines disappear when only the clock moved. The database counts are the one thing the file lacks (the daemon cannot read the database): the same store asks the control plane's `GET /api/developer/v1/dev-host/status` (`getDevHostMigrate` in `developer-client.ts`, the view the web interface's Development Host bar reads, so there is one source) for `host.migrate`, at most every 30 s and again when a job ends, only while the file is there, with a 5 s timeout and beside the file read so a hung or restarting control plane never holds the file back; a failed read keeps the last counts until they are 3 minutes old. A Services row gets a short note only when its part needs something, for example `↓3 · restart · install · local changes` or `on branch fix-x` (`migrate N` on the control plane row comes from those counts); the selected row also gets its full lines above the detail pane in the bar's words (`devHostPartLine`, `devHostDatabaseLine` in `src/lib/dev-host-status.ts`, kept in step with `../ui/src/lib/development-host.ts`): `Control Plane: detached at 4f7b5ed, 19 behind trunk, will not pull` from the daemon's `blockedReason`, and on the control plane row `Database: 23 of 25 migrations applied`; the notes widen the list to at most 45% of the width and are hidden once the file is older than 3 minutes (the daemon stopped writing); a stale file that still says a job is running counts as no job (no line, normal polling, actions allowed). While a job runs, or for 15 minutes after it failed, one line above the detail pane, and in the Developer subtitle row (so the menu never grows), names the step in plain words (`Update and Restart: restarting the control plane (step 5 of 7)`, or the failed step and its last output line). Developer → **Update and Restart** (`update-restart`) and **Restart Only** (`restart-only`), offered only on the developer-surface build and listed last before Purge so the default cursor never sits on a restart (a successful request shows `Started Update and Restart…` until the job line takes over), call `POST /api/developer/v1/dev-host/update` or `/restart` through `developer-client.ts` (`postDevHostAction`, same Local-Console signing as the other developer calls). The daemon does every step: fetch, fast-forward pull only for checkouts on trunk without blocking changes, `pnpm install` where the lockfile moved, a migration with a backup first, then restarts in order (control plane, web interface and website, the daemon last). The console never runs git, pnpm or systemctl for these actions. A 409 (`job_running`, a host job or the web Build and Push is running) and a 503 (`daemon_unavailable`, with `not_development` or `timeout` as the reason when given) are shown in plain words; the console also refuses on its own while the file shows a job running, since the control plane may be restarting then. Progress keeps moving while the control plane restarts because it comes from the file. Do not run the console **U** rebuild while a host job runs: the job may be pulling the daemon checkout that the rebuild compiles.

## Code Style

### TypeScript style (SonarQube)

- Prefer **`String#replaceAll()`** over **`String#replace()` with a global regex** when replacing every occurrence of a substring (`typescript:S7781`).
- Use **`String.raw`** for string literals that contain backslashes so escapes stay readable and correct (`typescript:S7780`). Example: POSIX shell single-quote escaping is `String.raw`'\''` plus `replaceAll("'", …)`, not `"\'\\''"` with `replace(/'/g, …)`.
- Import **`shellQuote`** from `src/lib/shell-quote.ts` for shell argument quoting — do not copy inline `shellQuote` helpers.
- Prefer **optional chaining** (`obj?.prop`) over `!obj || obj.prop` (`typescript:S6582`).
- Use **`new TypeError()`** (not `new Error()`) when asserting types/shapes in tests (`typescript:S7786`).
- Avoid **nested ternaries** — use `if`/`switch` or small helpers (`typescript:S3358`).
- Extract helpers when **cognitive complexity** exceeds 15 (`typescript:S3776`).
- Sort strings with **`.sort((a, b) => a.localeCompare(b))`** (`typescript:S2871`).
- Do not leave **`TODO`** in code — use `Future:` in a normal comment (`typescript:S1135`).
- Use **`RegExp.exec()`** instead of `String.match()` when extracting a single match (`typescript:S6594`).
