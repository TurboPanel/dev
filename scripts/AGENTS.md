# Shell Scripts (`scripts/`) — AGENTS.md

Repo context: `../AGENTS.md`.

## Shell libraries

- **`scripts/lib/privileges.sh`** — POSIX sudo re-exec helpers (`tp_ensure_privileges`), logging helpers, `tp_is_interactive()` (stdin TTY or readable/writable `/dev/tty`).
- **`scripts/lib/paths.sh`** — `/opt/turbopanel` path constants; pinned `NODE_VERSION` + vendored `NODE_BIN`/`PNPM_BIN` under `vendor/node/current/bin/`; pinned `DENO_VERSION` + `VENDORED_DENO_BIN` (`vendor/deno/current/deno`).
- **`scripts/lib/packages.sh`** — apt prerequisite checks: `tp_require_host_commands` (curl/tar/sha256sum).
- **`scripts/lib/runtime.sh`** — pinned **Node** install from the `nodejs.org` tarball into `/opt/turbopanel/vendor/node/<version>/` plus Corepack/pnpm (`tp_ensure_node_runtime` / `tp_ensure_corepack_pnpm`; Corepack is `npm install -g` on Node 25+); `tp_export_deno_path` prepends vendored Deno for hooks/child shells.
- **`scripts/lib/dev-identity.sh`** — resolve dev user from process UID (`tp_resolve_dev_identity`).
- **`scripts/lib/dev-prerequisites.sh`** — curl/sudo/dev-user checks for `./console`. When sudo still requires a password, optionally prompts to install `/etc/sudoers.d/turbopanel-dev-nopasswd` (full `NOPASSWD` for the dev user on local dev hosts). Set `TURBOPANEL_DEV_SKIP_NOPASSWD_SUDO=1` to skip the prompt.
- **`scripts/lib/git-github-ssh.sh`** — git identity prompts, SSH key generation, GitHub verification (used by `./console` when needed).

## Contributor Setup (`setup.sh`)

- **`scripts/start.sh`** is the no-clone entry: `curl -fsSL https://raw.githubusercontent.com/TurboPanel/dev/trunk/scripts/start.sh | sh` (options after `sh -s --`), or download, read, then `sh start.sh`. It must run on its own (no `lib/` sourcing, no `$0`/`SCRIPT_DIR`, since `$0` is `sh` when piped), and the whole body is `tp_start_main` called on the last line, so a cut-off download never runs and nothing is left on the pipe for a child to read. It refuses root, needs `git` and `curl` or `wget` (install hints otherwise), takes `--dir` (absolute, folder named `turbopanel`, same character and `.`/`..` rules as `tp_validate_dev_root`; default `$HOME/turbopanel`) and refuses a folder that is itself a git checkout (not one merely inside a repo, so a home-folder dotfiles repo does not block the default). An existing `<folder>/dev` must be a checkout with a remote pointing at TurboPanel/dev (origin or upstream) and is reused; otherwise it clones `https://github.com/TurboPanel/dev.git` with `GIT_TERMINAL_PROMPT=0` into `<folder>/.start-clone-dev` and renames it on success. It prints the plan (folder, clone, the `setup.sh` command, one line each on Vagrant and Direct), then `exec`s `sh <folder>/dev/scripts/setup.sh <other args> --dir <folder>`, with stdin from `/dev/tty` when stdin is not a terminal and `/dev/tty` opens, so setup's questions reach the keyboard under `curl | sh`. `--dry-run` without a dev checkout clones nothing and says setup's own dry run needs the files; with one it is passed on. No sudo, nothing installed. Tests: `src/lib/start-script.test.ts` (stubbed `git` clone; the terminal case runs the real `setup.sh` under util-linux `script` and is skipped where that is missing). Not provable in CI: a real clone from GitHub and a run on a fresh Debian 13 VM; the raw URL tracks `trunk` (a pinned tag with a checksum is later hardening).
- **`scripts/setup.sh`** is the one entry for every contributor; `doctor` and `status` are its read-only subcommands. It reads the repo list from `repos.list` (name, default branch, optional `optional` flag), and `vagrant-up.sh` reads the same file.
- **Folder:** all repos sit in one folder, by default the folder named `turbopanel` that holds this checkout, else `./turbopanel` (next to the dev checkout when run from inside it); `--dir` overrides and is normalised, and a folder inside the dev checkout is refused. The mode file is `<folder>/.turbopanel-dev-mode` (the folder that holds the repos, not its parent), shell-sourceable `key='value'` lines: `TURBOPANEL_DEV_ENV` (`direct` or `vagrant`; never `TURBOPANEL_MODE`, which means development versus production), `dev_root`, `clone_protocol`, `github_login`, `role_<repo>` (`role_github` for `.github`), `created` (kept across reruns) and `updated`. Scripts read it with `sed`, not by sourcing it; `ci-verify.sh` reads `TURBOPANEL_DEV_ENV` from `$REPO_ROOT/../.turbopanel-dev-mode`. `./console` reads `dev_root` from the same file (`tp_load_dev_root_mode_file` in `lib/paths.sh`) when `TURBOPANEL_DEV_ROOT` is unset; an explicit value wins, and when `dev_root` names another folder the folder that holds the file wins, with a warning.
- **Roles** come from `gh api repos/TurboPanel/<repo> --jq .permissions.push`: `maintainer` (origin = TurboPanel repo, no upstream), `contributor` (no push access, or `--as-contributor`, old name `--fork`, which warns: a read-only clone, origin = TurboPanel repo, no fork; forks are made on first push), `contributor-fork` (origin = the user's fork, upstream = TurboPanel repo; after `setup.sh fork <repo>`, or at setup with `--fork-all`) or `readonly` (not logged in). `setup.sh fork REPO...` takes names from `repos.list` (`.github` only when named), needs a mode file (it reloads `TURBOPANEL_DEV_ENV` from it before rewriting it, so the mode is never lost), `gh` and a login that answers (it refuses offline or logged out and changes nothing), then per repo runs `tp_ensure_fork` and `tp_reconcile_remotes` (origin renamed to upstream, the fork added as origin), fetches both, sets the default branch to track `upstream/<branch>` and records `contributor-fork`; branches and commits are never touched, a checkout already fork-shaped is a no-op, and an origin that is neither TurboPanel nor the fork is refused. A fork-shaped checkout counts as `contributor-fork` whatever the mode file says (files written before this said `contributor` for forks). Each `contributor-fork` checkout gets `gh repo set-default TurboPanel/<repo>` (best effort, a warning when it fails), so `gh pr create` does not ask which repository. `status` shows `maintainer`, `read-only` or `forked`; `doctor` prints the exact `setup.sh fork <repo>` for each read-only clone when logged in, as information, not a problem. The end of `setup` and `status` prints one plain-words sentence for the most common role (`tp_role_summary`) and lists the repos with another role on an `Except:` line. `.github` is never forked for anyone: a fork of an org's `.github` repo becomes the user's own account-wide community health repo. An API failure, an answer without `permissions` (never forked on an unclear answer) or no answer to `gh api user` while `gh` holds a token keeps the login and roles from the last run. The fork is found as `<login>/<repo>` or, when renamed, in the repo's fork list by owner; a checkout whose origin already is the fork needs no GitHub call, so offline reruns work.
- **GitHub CLI:** before the plan (gh and the login decide every role), a missing `gh` on Debian, Ubuntu or an `ID_LIKE` derivative with `apt-get` is installed the way the official install guide does it: download `githubcli-archive-keyring.gpg`, check with `gpg --show-keys` in a throwaway `GNUPGHOME` that the file holds only public-key records (any `sec`/`ssb` or unknown record fails closed), that every primary key has a fingerprint and that each is one of the published fingerprints (`GH_KEY_FINGERPRINTS`; pinned instead of the keyring checksum, which changes on every key rotation), install it to `/etc/apt/keyrings`, add the `signed-by` source and `apt-get install gh`, all through sudo (an empty `dpkg --print-architecture` stops it, and the temp folder goes on exit or Ctrl-C); `curl` and `gnupg` are installed first when missing. On a terminal it asks first; `--yes` installs without asking; with neither it only warns, as do other hosts (macOS: `brew install gh`). `gh auth login` is offered only on a terminal without `--yes`, runs on `/dev/tty` and the user signs in there; the script never types, reads or passes a token or password. `--dry-run` lists both steps and runs neither; `doctor` stays read-only.
- **Safety:** clones go to `<folder>/.setup-clone-<repo>` and are renamed on success; reruns fetch with `GIT_TERMINAL_PROMPT=0`, fast-forward the default branch only when it is clean and checked out here, or checked out in no worktree at all (then through `git fetch . <ref>:refs/heads/<branch>`, which only fast-forwards), and never reset, stash or switch. An existing `core.hooksPath` other than `.githooks` is left with a warning, and `doctor` only warns about it too (an unset one is a problem). An existing folder that is not a checkout, or a remote it does not recognise, is left alone with a message.
- **Direct mode** runs `sudo env TURBOPANEL_DEV_ROOT=<folder> sh vm-bootstrap.sh <user>` once and is offered only on Debian 13 outside a container; macOS and other hosts get Vagrant only. It refuses a folder not named `turbopanel` (owner rule: repos live in `~/turbopanel/<repo>` or another `turbopanel` folder, never directly in `$HOME`, the Vagrant guest included, which mounts them at `~/turbopanel/<repo>`), and a folder that is itself a git checkout. `tp_validate_dev_root` (`lib/paths.sh`), `vm-bootstrap.sh`, `resolveCheckedDevRoot` (`src/lib/dev-root.ts`) and the dev playbook apply the same rule; the default root is `$HOME/turbopanel`. The guest marker `/etc/profile.d/turbopanel-vagrant.sh` only picks the message for an old guest still mounting `~/<repo>` (rebuild with `vagrant destroy -f && vagrant up`, or the faster `vagrant reload --provision` followed by Reset development environment), plus setup.sh's Vagrant-guest checks; `TURBOPANEL_VAGRANT_GUEST_MARKER` is a test-only override for both `lib/paths.sh` and `setup.sh`.
- **Not provable in CI:** the real apt install of `gh` and the interactive `gh auth login` (the tests stub `sudo`, `apt-get`, `curl`, `gpg` and `dpkg` and drop `gh` from the path); the fork call (`gh repo fork --clone=false`, then polling until the fork answers) and the permissions API need a real GitHub login; the tests in `src/lib/setup-script.test.ts` stand in a fake `gh` and `file://` bare repos (`TURBOPANEL_SETUP_REMOTE_BASE`, `TURBOPANEL_SETUP_OS_RELEASE`, `TURBOPANEL_SETUP_FORK_WAIT` are test-only overrides).

## Shell Conventions

- Shell scripts are **POSIX `sh`** — no bashisms. Sonar `shelldre:S7688` (`[[` vs `[`) and `shelldre:S7682` (explicit `return`) are ignored in `sonar-project.properties` / `.sonarcloud.properties` for that reason.
- Developer identity (`TURBOPANEL_DEV_USER`, `TURBOPANEL_DEV_UID`, `TURBOPANEL_DEV_GID`) is resolved from the **process UID** via `getent passwd` (`tp_resolve_dev_identity()` in `scripts/lib/dev-identity.sh`). **`USER` / `LOGNAME` are never trusted.** Unresolved identities and `root` are rejected; the only root exception is a validated `SUDO_USER` passwd entry when the console runs under `sudo`.
- Node is pinned in `scripts/lib/paths.sh` (`NODE_VERSION` **`26.7.0`**), downloaded from `nodejs.org`, vendored to `/opt/turbopanel/vendor/node/<version>/` with a `current` symlink. pnpm is pinned solely by `packageManager` in `package.json` and provisioned via Corepack. Node 25+ dropped the bundled `corepack` binary, so `tp_ensure_corepack` installs the standalone package with vendored npm into that prefix before `corepack enable` / `prepare`. `tp_corepack_env` sets `COREPACK_DEFAULT_TO_LATEST=0` and `COREPACK_ENABLE_AUTO_PIN=0` so `pnpm --version` after `corepack prepare --activate` stays on that pin (Corepack otherwise reports the newest npm release when `./console` is launched from `$HOME`, which produced `expected vX, got Y` on every bump). The version check runs from the checkout so Corepack reads that `package.json`.
